# Weekly competition: release preparation

This feature is local only. None of the following remote changes has been performed. Publication needs approval for this batch.

## Preview and tests

- `npm run dev:competition` opens http://localhost:4186/competition/ using an isolated local PostgreSQL-compatible database. It does not write production content.
- For a fresh local learner attempt: `npm run dev:competition -- --reset-demo`. Only the local demo learner is reset; sample standings remain.
- `npm run test:competition` tests the real SQL gateway and shared backend against an ephemeral PGlite database.
- `npm run test:competition-browser` requires a fresh preview on port 4186 and Microsoft Edge. It drives one headless browser, blocks external requests, and tests a complete ranked QA attempt plus guest practice. Screenshots and the PNG result card are written under ignored `artifacts/competition-preview/screenshots/`.
- Sample players and the public QA fixture are explicitly labelled and must never be used for a real ranked competition. The loopback demo token is generated at startup and is accepted only by the local preview handler. The deployed function always validates Firebase tokens.

## Privacy, traffic and limits

Public fields: chosen name, opted-in Google picture, score, completion time, rank and result UUID. Firebase UID, private paper, answers before closing, review reasons, service keys and IP HMACs are never included in public results. Raw IPs are used transiently by the trusted proxy and are not persisted by this feature. HMACs rotate per Pakistan calendar week; expired rate records are cleaned up. Cloudflare/Supabase platform logging is governed by their own settings.

One Firebase UID gets one ranked attempt per Pakistan calendar week across all rounds. Google Auth is not proof of one real human per account. Another device, account, or outside helper cannot be reliably excluded without invasive proctoring. No camera, microphone, DevTools blocking or browser fingerprinting is added. Per-question backend deadlines and locked answers reduce assistance opportunities without claiming a cheat-proof exam.

The client does not poll the database for every countdown tick. Public data is cached for 30 seconds; private responses are always `no-store`. Answer changes use optimistic version checks; database uniqueness enforces weekly eligibility. Targeted indexes support expiry and score lookups. Account/network limits reduce abuse, with a higher shared-network allowance. Valid-account floods can still consume free quotas. Monitor provider dashboards before increasing traffic; no billing was enabled, and unlimited free concurrency is not promised.

The competition route remains `noindex` until the release is ready. Production build, deployed integrations, traffic/load testing, real-device Web Share and actual Google/Turnstile end-to-end checks remain release tasks. Existing site publishing pipelines and services were not run remotely during this work.
